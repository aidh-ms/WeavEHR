# Documentation design and maintenance

The documentation should let a reader **produce, inspect, and adapt a trustworthy
result** without first learning the package internals. This is the editorial plan
for contributors, including automated coding agents.

## Readers and their routes

These are design hypotheses based on the package's workflows, not findings from
user interviews. Validate them with new users as the project grows.

| Reader | Immediate question | Route and success condition |
| --- | --- | --- |
| Researcher evaluating the package | Can I get a useful result without access paperwork? | Synthetic tutorial → three expected heart-rate rows |
| Analyst with a downloaded database | What path/version do I use, and what files come out? | Run a dataset → inspect one concept and its coverage |
| Multicentre researcher | Does this variable mean the same thing in each source? | Catalogue → effective mappings → identity/time and clinical definitions |
| Clinical methods researcher | Why does this score differ, and does it use future evidence? | Clinical methods → parameters, missingness, timing, source references |
| Data engineer adding a hospital | Which part do I extend? | Add a table/concept → small-frame validation → inheritance |
| Contributor maintaining the engine | Where does this behavior live, and what must I update? | Architecture → focused API → relevant tests and canonical docs page |

A novice should not need registries or inheritance to complete the first tutorial.
An experienced user should not need to repeat that tutorial to find a field or an
error explanation.

## Lessons adopted

| Example | Useful pattern | Application here |
| --- | --- | --- |
| [Diátaxis](https://diataxis.fr/start-here/) | Separate learning, doing, understanding, and lookup | Tutorial, how-to guides, mental model, reference |
| [Django](https://docs.djangoproject.com/en/dev/) | Route readers by their task and experience | Explicit entry points and a small, purposeful navigation |
| [Polars](https://docs.pola.rs/user-guide/getting-started/) | Concrete input, executable operation, visible output | Tiny synthetic dataset with exact expected rows |
| [scikit-learn](https://scikit-learn.org/stable/getting_started.html) | Teach a small public API before the full machinery | Project → extraction → concept; API reference later |
| [SQLAlchemy](https://docs.sqlalchemy.org/en/20/tutorial/) | Explain layers and who needs each | Distinguish users running bundled configs from authors extending them |

These are selected practices, not a claim that one documentation system is universally best.
The existing Material/MkDocs stack is sufficient: familiar navigation, search,
copyable code, restrained colour, light/dark themes, and local system fonts.

## Content boundaries

| Location | Owns | Does not own |
| --- | --- | --- |
| README | Purpose, one command path, entry links | Full configuration manual |
| Start here | One successful lesson and the core mental model | Every installation or architecture option |
| How-to guides | One reader goal, prerequisites, steps, verification | Exhaustive API fields |
| Reference | Exact fields, generated inventory, method semantics | Promotional claims |
| Contribute | Architecture, workflow, editorial and comment policies | A second user manual |
| Dataset README | Source-specific representation and limitations | Repeated framework explanations or hand-counted coverage |

Give each fact one canonical home. Link to it elsewhere. Keep the original
getting-started and user-guide URLs; the former architecture URLs point to the
consolidated architecture page. Generated catalogue pages replace manual counts.
The Python API is curated around useful entry points rather than mirroring every module.

## Why the redesign was necessary

The previous walkthrough used removed `config_files`/`dataset_configs` fields,
omitted required dataset versions, and showed a wrong concept output path.
It also described automatic dataset/table prefixes that current code does not add,
and called the implemented sharding step unfinished. Placeholder architecture pages
and broad autogenerated API listings obscured the useful material. The replacement
was checked against implementation and tests, not merely rewritten from those pages.

## Keep examples executable

1. Update the canonical page when behavior changes. Do not append a new mini-guide
   to the README or a vaguely related section.
2. Prefer including a checked-in example file with `pymdownx.snippets` over copying it.
3. Update `tests/test_documentation.py` when changing the quickstart, transformer
   example, or complete step-config examples. The tutorial must run without credentials.
4. Run `uv run mkdocs build --strict`. Missing pages, anchors, snippets, or API
   targets must fail the check; do not silence them to make the build green.
5. Inspect the landing page, a guide, and a dense reference page at desktop and
   narrow widths when changing the theme or navigation.

Preview locally with `uv run mkdocs serve`. CI also uploads a `documentation-site`
artifact after the strict build and link check. Download and extract it, run
`python -m http.server 8000` inside the extracted directory, and open
`http://localhost:8000`. Serving it over HTTP enables directory links and search.
This artifact is a review preview, not a public documentation deployment.

Catalogue generation uses effective configs, including inheritance, and excludes
empty simple mappings from availability counts. It deliberately does not label a
mapping "validated". Pin sources and record deviations in the source index and
method notes; runtime outputs still require cohort-specific validation.

## Acceptance tasks for the next new user

Ask a researcher unfamiliar with the repository to complete these tasks without
maintainer help. Record where they stop; fix the page at that point.

- Produce the synthetic result and explain the fourth source row's absence.
- Identify the raw-data root and exact version for their dataset.
- Find whether a requested concept has a non-empty mapping in two sources.
- Change a mapping, inspect a tiny frame, and rerun the correct step.
- Explain the subject key, a score's lookback, and whether its evidence is retrospective.

Aim for a first visible result within ten minutes after installation. This is a
usability target, not a measured benchmark. CI verifies mechanics; it cannot replace
watching someone use the documentation.
